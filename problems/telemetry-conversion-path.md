# Стратегія: як телеметрія конвертується по шляху MQTT → база

**Компоненти:** Hardware → Mosquitto → MqttToRabbitMq → RabbitMQ → {RawLog, WebTier, DbWriter → Azure SQL}
**Тип:** дизайн-стратегія (навіщо саме такі перетворення й де вони стаються).

---

## 1. Три «форми» одних і тих самих даних

Телеметрія існує у трьох формах, і кожна — оптимальна для свого місця:

| Форма | Тип | Де | Навіщо саме така |
|---|---|---|---|
| **Словник** | `Measurement`/`Unit` (enum) | у коді | строгість, компілятор ловить одруки |
| **Дріт** | `TelemetryMessage` + `TickSample[]` | MQTT/RabbitMQ (JSON) | компактна ПАЧКА: спільні поля раз, семпли масивом |
| **Сховище** | `Tick` (рядок) | Azure SQL | плоский РЯДОК під індекси й запити історії |

Після сушки всі три живуть в одному проєкті `Oilgas.Model` — тож конвертація між ними це кілька рядків без міжпроєктних хопів.

## 2. Шлях і що на кожному кроці

```
Hardware
  │  генерує значення (baseline+noise, clamp, round за Measurement)
  │  enum → snake_case рядок на дроті (intake_pressure, esp_pump)
  ▼
TelemetryMessage {                         ← ПАЧКА (одне повідомлення)
  deviceId, deviceType, field, well,       ← спільні поля РАЗ
  timestamp,
  samples: [ {name, value, unit}, ... ]    ← N семплів
}  --JSON-->  MQTT topic oilgas/north/w12/esp_pump/esp_pump-001/telemetry
  │
  ▼  MqttToRabbitMq: БЕЗ конвертації (pass-through байтів),
  │                  topic → routing key (/ → .)
  ▼
RabbitMQ topic-exchange  oilgas.north.w12.esp_pump.esp_pump-001.telemetry
  ├──► RawLog     : БЕЗ конвертації — показує сирий JSON
  ├──► WebTier    : subscription — БЕЗ конвертації (сирий payload у LiveEvent)
  └──► DbWriter   : ← ЄДИНА конвертація
         десеріалізує TelemetryMessage,
         РОЗКЛАДАЄ пачку на рядки:
           для кожного sample →
             Tick { deviceId, metric=name, value, unit, timestamp }
                     ▲ deviceId/timestamp беруться з конверта пачки
         EF Core INSERT → Azure SQL
  ▼
WebTier queries:  Tick (рядки) → GraphQL (devices/ticks/stats)
```

## 3. Чому саме так — оптимально

1. **Рівно ОДНА конвертація, і в правильному місці.** Дріт→сховище стається лише у DbWriter, на вході в БД. Скрізь інше — це байти (bridge) або сирий рядок (rawlog, subscription). Ми не конвертуємо «про запас».

2. **Пачка на дроті, рядки в БД — це не забаганка, а ефективність.**
   - На дроті `deviceId/field/well/timestamp` йдуть **раз** на пачку з N семплів. Якби ми слали одразу «рядками» (`Tick[]`), ці поля дублювалися б у кожен семпл → зайвий трафік на кожному тіку кожного пристрою.
   - У БД навпаки — плоский `Tick` з `(deviceId, timestamp)`-індексом ідеальний під запити історії/графіків. Пачку туди класти не можна (не поіндексуєш семпли всередині JSON).
   - Тобто форма різна саме тому, що **вимоги різні**: дріт цінує компактність, БД — індексованість. «Розкладання» пачки на рядки — це і є перехід між цими вимогами.

3. **Enum усередині — рядок зовні.** `Measurement` (enum) перетворюється на `snake_case` рядок один раз, у Hardware; далі він так і їде на дроті й лягає в колонку `Metric`. БД читабельна, а між шарами нема enum-зчеплення.

4. **Bridge нічого не розбирає** (pass-through) — нуль CPU на гарячому шляху; він не власник схеми. Хто хоче форму — той і десеріалізує (DbWriter). Див. `mqtt-rabbit-bridge.md`.

5. **Fan-out дає різним споживачам різні потреби без конфлікту:** rawlog хоче сирий текст, subscription — теж сирий (жива стрічка), db — типізований рядок. Кожен бере зі спільного exchange те, що йому треба, і конвертує (або ні) сам.

## 4. Урок

Конвертуй дані **один раз і на межі, де змінюються вимоги** (тут — вхід у сховище). До того — неси як є. Різні форми (пачка/рядок) — це не дублювання, а відповідь на різні вимоги дроту й БД; уніфікувати їх «заради одного класу» означало б програти або в трафіку, або в індексації.
